# K9 Post Studio engineering instructions

## Scope and stack

- React + TypeScript + Vite, Tailwind, Cloudflare Workers with the official Vite plugin, D1 migrations, maintained Telegram Mini Apps SDK (`@tma.js/sdk-react`), Telegram HTTP Bot API.
- Phase 1 authentication/dashboard and Phase 2 rich editing/drafts/templates/media are implemented. Phase 3 publishing, live-preview preparation, scheduling and the Python controller are implemented at the user’s explicit request. Live channel sends, deployment and remote mutations still require separate approval. Business callback workflows are not implemented.
- Keep the app at the repository root. Keep Worker, UI, shared contracts, and database migration concerns separate.

## Security boundaries

- Every Mini App `/api/*` endpoint must authenticate raw Telegram initData server-side, verify HMAC and freshness, then enforce `OWNER_TELEGRAM_ID`. The explicit `/api/cli/*` and `/api/bridge/*` namespaces use separate scoped HMAC credentials, timestamps and D1 nonce reservation; it must pass the same owner/resource business rules.
- Never trust initDataUnsafe or SDK-parsed identity, use browser auth overrides, or add public signup.
- Invalid auth is 401, valid non-owner is 403, missing configuration is 503. Do not return upstream details or internal SQL errors.
- Keep all credentials in Cloudflare secrets and local ignored `.dev.vars`. Never place secrets in `VITE_*` values or commit/log launch data, tokens, IDs from real accounts, or webhook secrets.
- Webhook requests require `X-Telegram-Bot-Api-Secret-Token`; only the owner in the owner's private chat receives `/start` responses or registers media. Never register non-owner/group media.
- Publish/edit/retry paths must call `requireApprovedChannel` immediately before sending, check current Telegram permissions, and prevent revoked destinations from receiving content.
- Do not deploy, apply remote migrations, register webhooks, or create remote resources without explicit user authorization.
- Production is `https://k9-pb.kimshikano.workers.dev/`; Worker target `k9-pb`, existing D1 database `k9-post-studio`, binding `DB`. Pin the verified existing UUID before deployment; never use a fake ID or create replacement resources. `npm run deploy:ci` performs a guarded deployment only, with provisioning disabled. Remote migrations require inspection, backup/rollback preparation and separate explicit approval. A main-branch push may trigger Cloudflare Builds and requires deployment approval during recovery. Credentials being present do not supply approval.

## Quality and data

- Maintain strict TypeScript including tests. Use parameterized D1 queries, transactional batches for multi-table mutations, SQL checks and indexes, and additive migrations once deployed.
- Preserve signed Unicode data exactly for authentication. Keep frontend navigation, dialogs, and controls accessible on mobile, respect safe areas and reduced motion.
- Keep empty/error/loading states functional. Label Phase 3 capabilities honestly; avoid fake analytics or fake publishing controls.
- Run `npm run check`; run local migrations for schema changes. Tests use Node 24 SQLite and isolated Telegram mocks.
- Update README and deployment/security documentation for API, schema, configuration, and security changes.

## Phase 2 editor boundaries

- Structured content lives in `shared/editor`; version 2 documents have stable UUIDs. Use strict runtime validation for every draft/template request and reject unsupported fields/cycles/depth/size violations.
- Preserve the distinction between structurally valid incomplete drafts and complete Telegram export payloads. Never serialize editor IDs, ownership, revisions or metadata into Telegram API fields.
- Use the verified official Bot API 10.3 wire mappings. Media blocks contain InputMedia objects, captions are rich caption objects, details use `summary`, and ordered lists specify `value`/`type`. Link button style is callback-only; enforce 1–64 UTF-8 callback bytes and at most 8 buttons per row.
- Keep editor application limits explicitly labeled as Studio limits; do not invent undocumented Telegram maxima. Review docs/TELEGRAM_RICH_MESSAGES.md before changing serializer fields.
- Draft writes and delete operations require current revisions. On conflict, preserve local work and offer reload/copy/backup; never auto-overwrite.
- New resource access must match the configured owner. Legacy owner-null records belong to the single-owner workspace and remain intact. Add migrations; never reset or replace migration 0001.
- Media IDs must come from authenticated owner webhook events or verified same-bot getFile responses. Preserve canonical IDs on repeated registration. No token-bearing file URLs, direct browser uploads or channel sends in Phase 2.
- Use Tiptap structured content and safe React rendering. Do not persist raw editor HTML or use unsafe HTML injection. Keep mobile selected-block properties inline and toolbar controls touch-friendly.
- Run the full Phase 1 and Phase 2 suite, strict type check, lint and production build after substantive changes. Keep screenshots/test reports clearly labeled as local synthetic validation; native Telegram and live Bot API acceptance remain separate checks.
- Button labels support plain text only in this editor: TDLib InlineButton permits plain/composite/custom-emoji text, not arbitrary formatting marks or URL entities. Reject existing incompatible labels on export without deleting draft data.
- Keep recovery free of initData/credentials. Device persistence requires owner opt-in, expires after seven days, and clears on successful save. Restore must retain the recovery's original revision; no silent overwrite of newer server data. Expiry UI is an untrusted hint and never authorizes or extends a session.
- Deduplicate owner media updates through the same D1 lease as /start. Completion/failure writes must match the acquired lease. The Telegram send/D1 completion crash window remains at-least-once; never promise exactly-once /start sends.

## Phase 3 delivery boundaries

- Cloudflare and Python reception are mutually exclusive. `bot.py` is a Python 3.12+ python-telegram-bot Application in explicitly selected Python mode, and starts no polling in Cloudflare mode. Preserve the existing webhook until a separately confirmed mode switch. CLI defaults read-only; validate method/path/body signatures, 60-second expiry, nonces and strict scopes before routing. Never log secrets or include them in repr/URLs/frontend builds.
- Source drafts, per-channel publication snapshots and immutable operation snapshots are separate. Preserve message IDs/revisions/history on deletion or editing. Stable operation IDs and expected revisions are mandatory for external actions. Never report success without a validated Telegram confirmation.
- Live permission/media checks and last-moment approved-channel checks precede every send. Do not enable paid broadcast or arbitrary chat destinations. Preview callbacks are inert. Native Worker fetch must retain its global receiver and use manual redirects; real workerd tests protect this runtime boundary.
- Cron runs once per minute with one job per invocation; it remains inactive unless SCHEDULER_ENABLED is exactly true. Claims use durable compare-and-swap leases. Retry only definitive transient failures; never retry uncertain sends/edits/deletes. Reconciliation is explicit owner observation and must be labeled accordingly. No exactly-once guarantee.
- Keep migrations additive. Migration 0003 preserves legacy publication records and leaves old schedules in legacy_review pending owner review. Remote schema state must be inspected and backed up before approved migration. Disable scheduling before rollback and preserve the ledger/nonces/history.
- Run Python compilation/unit tests, the complete JS suite, strict types, lint, build and formatting. Use tests/phase3-runtime.mjs only as a local synthetic gateway with isolated workerd/D1 and intercepted outbound calls; its __qa endpoints must never enter production. Live Telegram, native Android, Windows and Termux checks remain separate.

## Phase 3.1 Python bot boundaries

- Follow docs/PYTHON_BOT.md. Use PTB 22.8, HTTPX and python-dotenv; preserve the old controller imports/commands without making the root executable CLI-only. Reuse Worker rich publishing, D1 storage and scheduling services; do not duplicate them or create a local DB.
- Validate both configured bot/owner identities and Web App URL through the signed bridge. Every Telegram handler must verify the owner ID AND private chat ID/type. Never authenticate a bridge request with an owner ID alone. Sign exact bytes/path/method with the separate bridge secret; retain expiry, D1 replay protection, scope whitelist and durable rate limits. Normal browser routes retain initData auth.
- Setup uses hidden inputs and refuses echoed fallback; config and webhook metadata are ignored private atomic files. Never print tokens, signed requests, updates or library exception URLs. --check must never change Telegram webhook configuration.
- Only explicit receiver confirmation may remove/restore the webhook, whether offered during normal startup or optional --switch-mode/--restore-cloudflare maintenance. Preserve metadata, require the existing Worker secret for restoration, refuse unknown integrations/custom certificates that cannot be backed up, and never discard pending updates. Use the durable transition fence and unique expiring polling lease. PTB bootstrap must never silently delete an existing webhook. Stop polling on lease/fence/conflict loss and release gracefully before switching.
- Keep menu callbacks epoch/message-bound and short-lived. Publishing requires preflight plus explicit confirmation, stable operation IDs and server checks. Unknown writes offer status inspection, never automatic resend; only known safe rate/transient rejections permit original-ID manual retries.
- Run Python compilation/pytest, actual PTB update/polling tests with synthetic transports, complete npm checks and local migration validation. No live Telegram sends, remote migrations, production receiver changes, secret rotations or deployment without separate approval. Keep legacy D1 data and migrations intact.
